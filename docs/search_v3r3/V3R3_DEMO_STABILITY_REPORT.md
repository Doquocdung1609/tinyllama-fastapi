# Windows Prebuilt stability and resource evidence

Run on the owner laptop, 30 October 2026, with `run_financial_studio.ps1 -Mode Prebuilt` on the isolated nine-PDF V3R3 owner clone. The launcher reported 9 PDF READY, OCR READY and SEC READY. The preparation endpoint reached READY after **113,745 ms** on first launch and **114,499 ms** after a controlled restart. The prepared generation remained the same; 11 source and on-disk index hashes matched across restart (`RESTART_INTEGRITY.json`). In-memory preparation still takes about 114 seconds after process restart. The UI exposes PREPARING/READY and low-memory warnings.

The 504 one-second samples over 577.7 seconds in `RESOURCE_SUMMARY.json` show: owned API peak **1,039.46 MiB**; aggregate Chrome peak **1,278.75 MiB**; Ollama plus llama-server peak **1,252.05 MiB**; Tesseract peak **0 MiB** because no new OCR job ran in this live demo; minimum available RAM **16.59 MiB**; minimum free disk **64.36 GiB**. Other applications were left alone. These are process RSS observations, not additive unique-memory accounting or leak evidence. The prior V3R2 observed minimum was 708.15 MiB; this run was materially more constrained by whole-machine activity. No application was closed automatically.

Five direct local Nomic embedding HTTP calls on the correct 768-dimensional model took **47.84, 51.73, 37.90, 38.12, 40.06 ms** (`EMBEDDING_LATENCY.json`). This measures the Ollama endpoint, not full retrieval. The prior same-laptop V3R2 OCR lifecycle measured **11,486.13 ms** from upload to READY for a raster derivative of SEM page 7 (`../search_v3r2/LIVE_OCR_LIFECYCLE.json`); no new OCR run was attempted under the observed low RAM, so **current-run OCR time is NOT_MEASURED**. The seven SEM regional OCR cells and their original checkpoints remain available.

The first Prebuilt browser batch was **4 PASS, 1 FAIL**: the initial reviewed CEO query received `LOW_MEMORY_DEFERRED` and the UI showed no hit. A single replay of that case passed, yielding all five scenarios independently PASS. Screenshots `screenshots/01-...` through `13-...` show reviewed source/highlight, negative abstention, three-arm comparison, stale-response protection, unreviewed candidate, SEM OCR/PDF/coverage, ACB and 20 page transitions, and PNJ. `.mjs` PDF worker MIME and highlight were verified on the passing replay. After restart, the same Chrome case again failed under low RAM, while a direct API query returned HTTP 200, five hits and the reviewed CEO assets row on PDF page 2 (`POST_RESTART_QUERY.json`). Thus source/index persistence and API recovery PASS; resource-constrained browser continuity PARTIAL.

The first preflight returned `WAIT_OR_REVIEW` with 287.19 MiB available; a later recheck returned READY with 1,029.19 MiB. The product search admission is 256 MiB and heavy-task admission 768 MiB; these gates prevented unsafe work but do not reserve RAM. A prior 178-query benchmark completed every query, yet its final repeat-prewarm was deferred below 768 MiB. Use the documented `scripts/preflight_search_v3r3.py` before presenting, wait for `production_v3r3` READY, and keep OCR/benchmark off during the demo. The evidence supports a conditional demo path, not an unconditional memory-stability claim.

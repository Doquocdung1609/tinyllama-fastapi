# P6 performance and resources

`python -m scripts.p6_performance_probe --root <owned-isolated-root> --output <p6_performance.json>` performed seven sequential exact P&G requests. Windows/Python 3.13.2; one 1,066,740-byte SEC HTML source, candidate budget 64, no GPU or Ollama. Process-cold first request was 3,744.719 ms; seven-run p50 2,828.230 ms and nearest-rank p95 3,744.719 ms. Process RSS rose from 46,759,936 to 117,747,712 bytes. `p6_performance.json` records per-run D1 parsing, candidate retrieval, complete source authentication/cell derivation, D4 typed numeric calculation and process RSS. "Cold" denotes the first call in that process, not an uncached disk reboot.

For the first run, D1 parsing was 5.184 ms, candidate retrieval 840.444 ms, source authentication/cell derivation 2,010.263 ms and D4 reauthentication/typed calculation 867.604 ms. The backend's one-time alias validation occurs before the inner stage timer and is included in the outer wall time. Repeated full-source validation dominates. These sequential figures are not throughput or concurrent-service capacity. No new persistent cache or vector index was installed. A future cache must key on raw SHA256, manifest, generation, parser/chunker identity and parent hash, rehash bytes on each request, invalidate on any mismatch and reject mixed generations before it can replace this path.

The real probe and live HTTP/browser JSON record other question latencies. D/F are ineligible for retrieval-quality comparison because compatible vectors were unavailable; no Recall@5 improvement is claimed from this policy.

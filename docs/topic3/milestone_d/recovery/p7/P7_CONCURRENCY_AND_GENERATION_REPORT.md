# P7 concurrency and generation safety

An isolated second clone was created from the original owned research snapshot. `python -m scripts.p7_concurrency_probe --root <second-clone> --output <p7_concurrency_results.json>` ran three parallel readers (nine queries) while publishing a new lexical generation, then three more reads. All 12 source-bound answers retained the old pinned generation and correct value; zero mixed-generation claims. The new generation became active only in that clone and the old generation remained READY. This does not test owner-data cleanup or multi-process distributed publication.

P7 separately changed the active clone generation state to FAILED while an API server was running. On P6, HTTP incorrectly returned 200/SUPPORTED/23,276,000,000. After `FrozenResearchSnapshot.search` required READY, the same live request returned 409/no value (`p7_invalid_generation_before.json`, `p7_invalid_generation_after.json`). A source replacement and warm-cache mutation were also refused in the tamper suite. Restart with the same manifest and token produced the original source-bound answer; unauthenticated requests after restart returned 401. A full manifest-switch publication/rollback test remains unverified.

# Financial QA validation boundary

The retrieval experiment verifies **locations**, not values. The four development candidates have original SEC HTML SHA-256, row locator, proposed period and unit in `../03_IMPROVEMENTS/STRUCTURE_TARGETS.json`; their labels are machine-prepared and remain `PROVISIONAL_UNREVIEWED`. The source parser marks both filings `PARTIAL_EXTRACTION`. No row is promoted to `VERIFIED` or passed into Decimal arithmetic from retrieval score alone.

`app/topic3/evidence_policy.py` is a conservative isolated research check. On the six exposed queries it returns three `SOURCE_SUPPORTED_UNREVIEWED`, one `AMBIGUOUS` for the P&G duration-period label, one `INSUFFICIENT_EVIDENCE` for the unsupported 2037 period and one `UNSUPPORTED_REQUEST` for absent Apple. All six have `numeric_answer_eligible=false`; the exact machine output is `../03_IMPROVEMENTS/CONSERVATIVE_EVIDENCE_ASSESSMENT.json`. Three unit tests pass for the current rules. It does not validate table-column geometry, scale, OCR digits or the candidate numeric values.

The existing product already separates PDF source snippets from source-reviewed numeric facts (`app/product/frontend_api.py` `/studio/analysis` and `app/product/analysis.py`). A small product repair now lets the React PDF document-QA flow use the same `production_v3` hybrid retrieval service as Search; callers omitting `search_profile` retain the old baseline behavior. The fresh-process Hòa Phát request returned five citations, top source page 3 and no numeric value. SEC numeric questions still use a separate research-QA backend (`/studio/sec/analysis`). The new structure-aware **research** index is not wired into either endpoint, so its four-question improvement is not claimed for the production UI. The one-question flow returns source excerpts or an already supported verified SEC cell, but it does not compose a free-form source-grounded PDF answer; G7 remains partial.
